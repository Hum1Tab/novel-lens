# 着手前 Go / No-Go 再審査

> 2026-08-31更新: 2026-08-30版の6～8週間は初期timeboxだった。研究運用、16 caseの独立annotation、二者evidence review、全spikeをissue見積りへ展開した結果、1 builder + 1 research leadの標準計画は10～12暦週へ改訂した。[Gate A backlog](./gate-a-backlog.md)を日程のauthoritative sourceとする。Go / No-Goの論理は変わらない。

判定日: 2026-08-30  
対象: KASANE（仮称）の構想、競争環境、技術前提、検証順序  
関連: [市場調査](./2026-writing-environment-research.md) / [プロダクト提案](./product-proposal.md) / [構造再検討](./structure-review.md) / [出典台帳](./source-register.md)

## 結論

現時点の判定は三つに分かれる。

|判断対象|判定|理由|
|---|---|---|
|構想の中心思想|**条件付き Go**|作者中心、AI任意、根拠と版を持つ所見、情報境界、日本語品質、退出可能性には一貫した価値がある|
|新しい統合デスクトップエディタの本開発|**No-Go**|近接OSSが急増し、乗り換え需要、AI所見の優位性、縦書き、正本形式、履歴方式、保守体制が未検証|
|標準10～12暦週の証拠作り|**Go**|read-only検証と既存OSS比較なら、正本を危険にさらさず最重要仮説を段階的に棄却できる|

したがって、今すぐ作るべきものは製品本体ではない。**「この製品でなければ解けない仕事が本当にあるか」を判定する証拠一式**である。

現段階でTauriの殻、章ツリー、設定DB、AIチャット、Git画面を作り始めてはいけない。それらはすでに複数製品が持ち、差別化の証明にならない。Gate Aを通過した後も、第一選択は新規開発ではなく、既存OSSへの貢献、拡張、または狭いcompanionである。新規コアは、不可欠な要件が既存基盤では構造的に実現できないと証明された場合だけ選ぶ。

## なぜ判定を厳しくしたか

初回調査後に、構想へ非常に近い2026年の実装が複数確認できた。

- [Linetta](https://github.com/devlikebear/linetta)はAGPLのローカル優先小説制作環境で、場面編集、アウトライン、人物・場所・関係・資料、SQLite保存、版スナップショット、日次バックアップ、Markdown入出力、任意Git同期、任意AI、提案→確認→適用を既に持つ。日本語UIと署名済みmacOS版、Windows/Linux配布もある。公開資料上の正本は`library.db`で、直接縦書きや版追従アンカーは確認できないが、本構想の一般機能の大半は重なる。2026年8月時点で利用規模はまだ小さく、需要を証明する材料ではない。
- [TsumugiMark](https://github.com/mofukuru/TsumugiMark)はObsidian上でMarkdownを直接縦書き編集し、日本語IMEを意識したタイプライターモード、複数のルビ記法、往復保存、外部変更検知、表示設定を実装している。β版でバックアップを勧め、禁則や全エッジケースを保証してはいないが、「Markdownの直接縦書きは原理的に無理」という前提は崩れた。
- [Vela](https://github.com/heider-x/vela)はローカルSQLite、RAG、BYOK、ローカルモデル、MCP、IDE風UIを持つOSSで、生成中心ではあるものの、「ローカルAI小説IDE」という説明は既に一般化している。
- [OpenNovel](https://github.com/Yaemikoreal/OpenNovel)はMarkdownを人間向け層、YAML/SQLiteを機械向け層として扱い、Git、正史、安全柵、根拠付き批評、提案と承認、差分・復元を組み合わせる。自動生成中心で対象は異なるが、データ設計の着想は大きく重なる。
- [Manuscript](https://github.com/DoktorDaveJoos/manuscript)はローカルSQLite、Tiptap、場面・設定、スナップショット、視覚差分、部分採用、BYOK AI、全稿チャット、版ガード、出版出力を持つ商用デスクトップ製品である。
- [TalePal](https://www.talepal.org/)はVS Code上でローカルMarkdownとローカル／クラウドAIを結ぶ。有料拡張であり日本語縦書きは確認できないが、「既存エディタへ小説向けAIを足す」代替経路を示す。

このため、**ローカル + AI + Git + Story Bible + IDE風UIは市場の穴ではない**。それらは実装可能な部品で、模倣も速い。残る可能性があるのは、次の狭い組合せである。

> 指定した読了位置までしか知らない模擬読者が、現在版へ解決できる根拠を返し、改稿後には追従または失効し、それを日本語の縦書き原稿と退出可能なデータで使えること。

これも未検証の差別化仮説であり、競争優位が確認された事実ではない。

## 事実、推論、未検証を分ける

|論点|現時点の証拠|判定|
|---|---|---|
|作家が複数ツールを併用する|日本・海外の実利用例が複数あり、工程別の理由も整合する|困りごとの存在は確認。頻度と市場規模は未確認|
|既存製品は全部入りでも摩擦がある|長編性能、詳細フォーム、出力往復、同期、退避への不満例がある|改善余地はあるが、新製品への移行意思とは別|
|根拠付きAI所見は役立つ|既存製品と研究で、具体的で概ね正しい所見が出る例はある|generic ChatGPTや人間読者より有用かは未確認|
|AIは作品を理解できる|支持できない。研究では重要問題の見逃し、批判判断の誤り、物語理解の弱さが確認される|製品文言として使用禁止|
|直接縦書きは実現可能|TsumugiMark等で実装例がある|製品品質、データ安全、Windows/macOS同等性は未証明|
|Gitを隠せば一般作家にも最適|Git利用例と履歴需要はある|Gitそのものが最適な内部エンジンかは未証明|
|人可読ファイルを正本にすべき|退出性、外部編集、差分に強い|stable ID、装飾、並替え、同時変更との両立方式は未証明|
|OSSなら信頼される|監査、退出、継続可能性に寄与する|導入、署名、サポート、maintainer確保を自動では解決しない|

この資料群は市場シェア調査ではない。Web上のレビューや投稿には選択バイアスがあり、新興GitHubプロジェクトの機能表は実作品での成熟度を示さない。価格受容性、寄付意向、移行率、4週間以上の継続率はまだ測っていない。したがって「市場の穴を発見済み」とは言えない。

## 最大の反証

### 1. 利用者は問題を抱えていても、エディタを替えない

小説家の原稿環境は、機能比較だけでは動かない。筋肉記憶、端末、編集者との受渡し、投稿記法、既存作品、同期への信頼が蓄積している。NolaやScrivenerに不満があっても、補助ツールを一つ足す方が安全である。

したがって「全部を一つにする」は価値提案ではない。最初に測るべき行動は、唯一の正本への移行ではなく、既存ワークフローと並行して二度目も使うかである。分析は使うが本文は移さないなら、それは失敗ではなく、companionまたはpluginが正しい製品形態だという証拠になる。

### 2. AI講評は見栄えがよくても、最大の問題を外し得る

[ACL 2025の1,300作品を用いた研究](https://aclanthology.org/2025.acl-long.1254/)では、モデルは具体的で概ね正確な所見を出す一方、最大の問題を見落とし、批判すべき時と肯定すべき時の判断を誤ることが多かった。[LREC 2026の日本語ショートショート研究](https://aclanthology.org/2026.lrec-1.159/)でも、複数モデルは人間より低く、皮肉、含意、感情の反転に苦戦した。

[LitBench](https://aclanthology.org/2026.eacl-long.362/)では最良の汎用LLM審査器でも人間の選好との一致は73%だった。[Style over Story](https://aclanthology.org/2026.findings-acl.1361/)は、モデルが出来事・人物・設定より文体を優先し、内容面の選好がモデル間で分かれると報告する。

よってAIを「編集者」や「品質判定器」として売ってはいけない。提供できるのは、**読んだ範囲と偏りが見える合成読書パス**である。

- 単一の作品品質スコアを出さない
- 「問題なし」「矛盾なし」を言わない
- 未検査、取得失敗、モデル間不一致を隠さない
- 数字の確信度を、文学的な正しさの確率として見せない
- 作者の声を一般的な「滑らかな文体」へ均す書換えを既定にしない
- 日本語・ジャンル・作品長・モデル別に評価する

AI所見の価値がgeneric ChatGPTへの同じ質問を明確に上回らなければ、AI部分は中止または補助へ格下げする。

### 3. Gitの利点とGit採用は別である

利用者が欲しいのは、入力の復元、日付で戻る、節目、別案、比較、遠隔退避であり、Gitオブジェクトではない。Gitを内部化すると、毎キー入力の自動保存、バイナリアセット、sidecar、外部編集、既存リポジトリ、OneDrive等の同期、競合復旧との境界が増える。

履歴はまず次の抽象契約として設計する。

1. ある時点の一貫したスナップショットを作る
2. 日本語の文・段落単位で比較する
3. 全体または場面だけを復元する
4. 名前を付けた別案を作り、元へ戻れる
5. 別媒体へ暗号化または標準形式で退避する

その実装候補として、ネイティブな不変スナップショット／内容アドレス方式とGit backendを同じ障害試験で比べる。Gitは互換アダプタまたはexpert modeになり得るが、libgit2をMVPの確定前提にしない。Linettaの「内部スナップショット + 任意のMarkdown/Git同期」は有力な比較対象である。

### 4. 開いた正本と壊れないアンカーは緊張関係にある

Markdownは読めて移動しやすいが、外部編集で段落UUIDやsidecarとの対応が壊れ得る。本文へ不可視IDを埋めると可読性と他ツール互換性が落ちる。SQLite等の構造化正本はIDを守りやすいが、アプリ外での可読性が落ちる。

固定するのは「Markdown正本」ではなく、次の利用者保証である。

- アカウントやサービスなしで全作品を回収できる
- 仕様が公開され、意味を失わない標準的なexportがある
- 検索索引とAI派生物を消して再構築できる
- migration、backup、restoreが試験できる
- 外部編集を受け入れる範囲と衝突時の挙動が明記される

Phase 1で少なくとも、Markdown + sidecar、ID付きMarkdown、構造化正本 + lossless exportの三方式を同じgolden corpusで比べる。思想で先に勝者を決めない。

### 5. 縦書きは差別化になり得るが、製品を沈める可能性もある

TsumugiMarkは直接縦書き、ルビ記法保持、外部変更検知まで到達している一方、β版としてバックアップを求めている。これは「実装可能」と「唯一の原稿を預けられる」が別であることを示す。

直接縦書きは、正本型エディタへ進む場合の厳格な品質ゲートとして残す。ただし価値検証用companionの前提にはしない。TsumugiMark、TATEditor、Nola、一太郎を基準に、IME、キャレット、選択、undo、ルビ、縦中横、禁則、注釈、外部変更、スクリーンリーダーを比較する。合格できない場合は、横書きだけの新規エディタを妥協公開するのではなく、既存縦書き基盤のpluginまたはcompanionへ留まる。

### 6. OSSはライセンスより運営が難しい

小説家が必要とするのは、ソース公開だけでなく、署名済みインストーラ、安全な更新、復元手順、脆弱性対応、互換性維持、問い合わせ先である。単独開発で全デスクトップOS、AI provider、DOCX、縦書きまで負うと、保守が新機能開発を上回る。

公開1.0前に、プロジェクトをどちらとして運営するか決める。

|運営目的|必要な判断|
|---|---|
|公共財型OSS|小さい範囲、無保証の明記、長期形式仕様、寄付と複数maintainer|
|持続可能な製品|有料サポート・同期・署名版等の支払意思、商標・release責任、資金計画|

二人以上がreleaseと復旧を担当できない限り、正本を預かる公開1.0へ進めない。フォークはupstreamとの合意が得られず、独立保守の人員と理由がある場合だけにする。

|要素|再審査後の扱い|
|---|---|
|作者が書くことを中心にする|固定原則として残す|
|AIなしで成立|固定原則として残す|
|読了位置による情報境界|最重要の価値仮説として検証|
|版付き根拠と古さ判定|最重要の技術・信頼仮説として検証|

|ローカル所有と退出性|固定保証として残す|

## 最初に比較する実装経路

|経路|強み|構造的な懸念|現時点の優先|
|---|---|---|---:|
|read-only companion|正本を変更せず、レンズ価値とアンカーを最短で測れる|執筆UXや履歴需要は測れない|1|
|Linettaへ貢献|小説用UI、ローカル保存、snapshot、AI安全フロー、配布を既に持つ|SQLite正本、縦書き、stable anchor、roadmap合意を要確認|2|
|Obsidian + TsumugiMark拡張|開いたMarkdown、既存Git・plugin生態系、直接縦書きがある|Obsidian依存、plugin間競合、一般作家への導入、正本保証の責任|2|
|novelWriter拡張／連携|成熟した長編構造、人可読ファイル、既存利用者|PyQtでの縦書きとAI所見UI、core境界|3|
|独立fork|既存資産を使いつつ方向を制御できる|upstream分岐、移行、release負担が累積|4|
|完全新規コア|全不変条件を一から設計できる|最も遅く、未検証需要へ最大投資|5|

「Linettaへ必ず載せる」とも「新規コアが必要」とも、まだ結論しない。まずmaintainerへ設計相談を行い、公開された拡張境界、正本形式、縦書きの方針、AI所見モデルをコードと試作品で確認する。4～5個の不可欠条件をupstreamで満たせるなら、新規コアは作らない。

## 標準10～12暦週の証拠作り

### 週1～2: 契約、対象、corpus、mockを固定する

- D0 2名 + D2有効8名を最低構成とする12謝礼枠を募集し、segment quotaを満たす
- 長編、Web連載、同人・文芸、プロット型・発見型、AI拒否・慎重・利用者を混ぜる
- 「欲しい機能」ではなく、直近のデータ不安、見落とし、改稿、出力、道具間往復を実演してもらう
- 研究利用許諾を分け、原稿を収集しない選択肢を用意する
- 公共財型OSSと持続可能な製品のどちらを目指すか、開発側の制約も明文化する
- 16本のC1 caseを実装者と分離して新規作成し、二人で独立annotationする
- immutable snapshot、hard cutoff、mock provider、strict anchorを先に作る

### 週3～4: 既存手段を観察し、controlled AI比較を準備する

同じ5タスクをNola/Scrivener、Linetta、novelWriter、Obsidian + TsumugiMark、汎用ChatGPT等で比較する。

1. 既存長編を開き、迷わず続きを書く
2. 指定章までの初見読者として混乱点を探す
3. 設定衝突の候補と二つの根拠を探す
4. 大改稿前へ戻り、別案を比較する
5. TXT/Markdown/DOCXへ出して元原稿と照合する

成功時間、やり直し、誤操作、信頼できない瞬間、別ツールへ逃げた理由を観察する。機能数を採点しない。

- 原稿のコピーだけを読み、初見読者と整合性候補の所見を返す
- 各所見に引用、対象版、読了位置、coverage、未検査範囲を表示する
- generic modelへの同等質問と、condition label/prompt/mappingを隠したA/Bで比較する。lens固有interactionは見えるため完全盲検と呼ばない
- Linetta MCP、Obsidian + TsumugiMark、strict anchor、長文coverageの早期spikeを行う
- production UI、独自project format、provider網羅、本文書換えは作らない

### 週5～6: masked comparisonとsafety gateを判定する

- 少なくとも8人・有効24 pairでgeneric/lensを比較する
- 所見の採用率だけでなく、却下時間、最大問題の見逃し、未来情報漏洩、文体を均す圧力を記録する
- safety gateを一つでも破れば新規sessionを止める
- value gate不通過なら後段の正本・履歴・縦書きspikeへ投資しない

### 週7～10: 4週間のparallel pilotとvalue-gated spike

- safety/value gateを通った場合だけ5人が元ツールを残したまま同じ実作品で4週間使う
- 元ツールを残したまま使い、二回目を自発的に起動するかを見る
- 「これがなければ現在の回避策へ戻るか」を尋ね、好意的感想より行動を重視する
- 同時にnovelWriter adapter、縦書き、正本三方式、native/Git履歴、配布をtimeboxする

recruitingまたはsafety修正で延びる場合、pilot期間を短縮せずGate Aを延長する。

### 週11～12: 独立評価と経路決定

- Linetta、TsumugiMark、novelWriterのmaintainer方針と技術境界を記録する
- 二人のmapping-masked raterが20%以上を重複評価し、supported/harmを監査する
- companion、upstream貢献、plugin、fork、新規コア、停止を同じ評価表で比較する
- 正本・履歴・縦書き・アンカーについてADRを作る。ただし不合格なら「未決」ではなく停止とする
- コーパス、評価手順、golden fixture、匿名化された失敗例を、権利上可能な範囲でOSS資産にする

## Gate A: 続行条件と撤退条件

数値は小規模探索の暫定閾値で、市場規模の証明ではない。開始前に測定方法と除外規則を固定する。

### 続行に必要な最低条件

1. D0を除く有効participant 8人・有効24 pair以上を得て、4週間pilotの5人中3人以上が促されず二回以上起動する
2. 同一model/input条件のcondition-label masked比較で、事前登録したpreference、participant多数、supported/harm、recallまたはnet useful rateの全閾値を満たす
3. 初見読者レンズの未来情報漏洩が、定義済みred-team corpusで0件
4. 表示アンカーは100%が現版へ解決するか、古い・曖昧と表示され、無言の誤付着が0件
5. golden corpusで本文、段落、空行、ルビ、傍点、区切りの意味損失が0件。表現上の差は明細化できる
6. 正本型エディタへ進む場合、Windows/macOSの定義済み縦書き・IME試験に実装経路がある
7. 既存OSSで不可欠条件を満たせるか、maintainerとの対話と試作を含む証拠がある
8. 公開1.0を目指す場合、二人以上のrelease・復旧担当またはその資金計画がある

### 即座に縮小または停止する条件

- AIレンズがgeneric promptを事前閾値で上回らない → lens投資を止めて失敗を記録する。日本語editor／履歴は別仮説として新しいgateなしに着工しない
- 分析は使われるが本文は移されない → standalone editorを作らずcompanion/pluginにする
- 直接縦書きが対象者の切替理由にならない → 新規縦書きエンジンへ投資せず、既存基盤と校正表示を使う
- round-tripまたはアンカーで無言の意味損失・誤付着を防げない → 正本を預かる製品へ進まない
- Linetta等で不可欠条件の大半を実装できる → 新規コアを作らずupstreamへ貢献する
- 一人でしかrelease・復旧できない → 公開1.0を名乗らず、研究的pluginまたはβに留める
- 4週間後に実作品で自発利用が残らない → 機能を追加せず、対象または構想を終了する

### 分岐規則

|観察結果|選ぶ経路|
|---|---|
|レンズ価値あり、エディタ移行なし|read-only companion / plugin|
|レンズ価値あり、Linetta等で不変条件を実装可能|upstream貢献|
|縦書き・開いた原稿が中心でObsidian利用が受容される|TsumugiMark連携またはObsidian plugin|
|統合利用が強く求められ、既存基盤が不可欠条件を構造的に満たせない|初めて新規コアを検討|
|レンズ価値も統合需要も弱い|停止|

## Gate Aを通った場合だけ作る最小製品

経路にかかわらず、最初の正本型製品は次へ絞る。

- 章・場面の本文、検索、横書き。standaloneなら合格済みの直接縦書き
- 保存、復元、日常履歴、節目、比較。backend名はUIへ出さない
- lossless import/exportと、アプリ削除後の退出手順
- 人間コメントとstable anchorを先に実装
- 初見読者と整合性候補のread-onlyレンズ
- 読了位置、引用、版、coverage、古さ、却下・意図的状態
- AI完全無効、BYOKまたはローカル一系統。原稿送信明細

本文生成、続きを書く、全面rewrite、品質スコア、複雑なtimeline、関係graph、共同編集、同期サービス、mobile完全版、plugin marketplace、EPUB/DTPは入れない。

## 本当に防御力になるもの

コード上の機能は追いつかれる。長期的な防御力になり得るのは次である。

1. 権利処理された日本語小説の評価コーパスと、自然な改稿失敗・伏線・叙述トリックを含む試験
2. 版付き所見、情報境界、coverage、失効を表す公開データ形式
3. Nola、Word、一太郎、Markdown、投稿記法を跨ぐlossless fixture
4. 日本語IME・縦書き・ルビ・注釈の再現可能な回帰試験
5. 誤りを隠さない評価結果、復元実績、移行手順
6. 作家、編集者、図書・出版、OSS maintainerが参加する小さく信頼できるcommunity

これは「機能の囲い込み」と逆である。仕様とfixtureを公開し、他製品も実装できるようにする。そのうえで最も信頼して使える実装と運営を提供する。

## 最終提案

方向性は捨てなくてよい。ただし、現行案をそのまま製品仕様として着工するのは誤りである。

2026年に目指すべきものは、一般的なAI小説IDEではなく、**作者が所有する日本語原稿に対して、読了位置を守った合成読書を行い、版付きの根拠へ戻れる、小さく検証可能な編集伴走層**である。最初は既存環境の横に置き、その価値と信頼が証明された場合だけ正本側へ広げる。

次の一手は製品本体の実装ではなく、標準10～12暦週のGate Aである。ここでcompanion、upstream、plugin、新規コア、停止のどれを選んでもよい。**新規アプリを作ることではなく、作者にとって最も小さく安全な解決経路を選べたことを成功とする。**
